- **Framework / runtime:** Nova Discord bot scaffold, discord.js, Node.js, and Docker

## Build and Tooling

### Prerequisites

Use a Node.js version permitted by the root manifest, npm, Docker with Compose support,
and the runtime credentials required by enabled bot capabilities.

### Commands

Use the root `dev`, `prod`, `check`, `build`, `deploy`, `clean`, `changelog`, and
`recipes` commands for repository-wide work. Nova orchestrates the root, bot, and
documentation workspaces from the configuration in `nova.config.json`.

| Command                                                 | Purpose                                       |
|---------------------------------------------------------|-----------------------------------------------|
| `npm run dev --workspace discord-stonker-bot-app-bot`   | Run the bot workspace in development mode     |
| `npm run check --workspace discord-stonker-bot-app-bot` | Run the generated lint, type, and test checks |
| `npm run build --workspace discord-stonker-bot-app-bot` | Transpile the bot for production              |
| `npm run deploy:container`                              | Build and start the Docker Compose appliance  |

### Environment Variables

The Discord token and enabled integration credentials must be supplied through the
documented runtime secret boundary. Never commit them or bake them into the image.

## Architecture and Data

### Architecture

- Keep the client bootstrap and event kernel small. Feature modules own their commands,
  event handlers, scheduled jobs, validation, and cleanup.
- Register a module only after its configuration validates and all required Discord
  permissions, intents, and external credentials are known.
- Separate Discord adapters from domain decisions so moderation and routing behavior can
  be unit-tested without a live client.
- Represent scheduled jobs explicitly, give each one a stable identity, and prevent
  duplicate registration across reconnects.
- Centralize outbound Discord and provider rate-limit handling rather than adding ad hoc
  delays inside features.
- Avoid shared mutable caches between unrelated capabilities. When shared state is
  necessary, give it an owner and a defined lifecycle.
- Keep external provider clients behind narrow adapters with timeouts and typed results.

## Project Guardrails

### Platform and Domain Rules

#### Feature Admission Rule

A legacy or new capability enters the rewrite only when:

1. A current user or operator problem is documented.
2. The required Discord permissions and intents are proportionate.
3. Configuration can be validated at startup.
4. Failure is isolated from unrelated modules.
5. Automated tests can cover its core decisions.
6. Its external API and maintenance burden are acceptable.
7. The feature matrix records retain, redesign, or replace with rationale.

Features marked defer or remove must not leave dormant handlers, dependencies, or
configuration keys in the new runtime.

#### Docker and Operations

- Build a reproducible image through the scaffold's Docker integration.
- Treat the root Dockerfile and `packages/docker/project/` as project-owned PostgreSQL
  specialization layered onto Nova's structural contract. A future scaffold pass may
  merge manifest services, but must not blindly replace that specialization or its
  stable commands with generic generated helpers.
- Run the long-lived bot as a non-root user and use a read-only filesystem where
  practical.
- Provide appliance liveness and readiness for the control panel, database, and required
  initialization. Publish Discord Gateway readiness separately so a stopped or
  misconfigured bot does not make the control plane unavailable.
- Handle SIGTERM and SIGINT by stopping schedules, draining bounded work, destroying the
  Discord client, and exiting within the container grace period.
- Keep state that must survive replacement outside the container.
- Pin base images and application dependencies according to Nova conventions.
- Emit structured, redacted logs with module and operation context.
- Send operator alerts to destinations configured in the control panel when the bot
  can't sign in, drops off Discord or comes back, a job gives up, panel sign-in locks an
  address out, or saved secrets are removed. Deliver them through the durable job queue,
  10 seconds per try with retries 30 seconds apart, so a slow or failing service never
  blocks the bot.
- Do not add an HTTP listener solely to satisfy health checks if the container runtime
  can use a narrower process health mechanism.

#### Discord Safety Guardrails

- Request only intents needed by enabled capabilities; privileged intents require an
  explicit feature justification.
- Check both Discord permissions and the configured trusted-role policy before every
  privileged action.
- Make destructive or bulk actions confirmable, bounded, auditable, and safe to retry.
- Treat Discord IDs as opaque strings and validate all interaction and message input.
- Do not assume cached members, messages, channels, or roles are complete.
- Respect interaction response deadlines and use deferred replies for longer work.
- Sanitize mentions and allowed-mention behavior in relayed or automated content.
- Never expose tokens, webhook URLs, member-private data, or raw provider errors in
  public Discord responses.
- Handle disconnect, reconnect, and duplicate delivery without repeating irreversible
  actions.

### Security, Privacy, and Secrets

#### Configuration and Secrets

- Validate configuration before logging into Discord or starting background jobs.
- Prefer a typed environment and configuration boundary produced by the Nova scaffold.
- Bootstrap secrets must come from runtime secret injection or be generated into
  persistent secret storage. Operator-managed integration credentials may enter through
  an authenticated control panel, but must be encrypted before persistence and must
  never be committed, rendered back to the user, logged, or baked into the image.
- Notification destination secrets, such as tokens, passwords, and webhook URLs, follow
  the same rule. If the credential key is lost, they are removed and their destinations
  stay paused until the secrets are entered again.
- A missing optional module configuration disables that module cleanly.
- A malformed enabled module fails startup with a path-specific, actionable error.
- Document configuration migrations; do not silently reinterpret a legacy key.
- Keep per-guild assumptions explicit until the single-guild versus multi-guild decision
  is resolved.

### Compatibility

#### Rewrite Boundary

- Build the replacement in `apps/bot` from Nova's Discord bot scaffold with Docker
  packaging.
- Treat `assets/legacy/src/`, `assets/legacy/config-sample.json`, and the legacy documentation as a
  behavior inventory, not a code structure to preserve.
- Do not port the legacy initializer or modules line by line.
- Do not promise feature parity until a feature matrix records an explicit decision for
  every legacy capability.
- Keep undecided legacy behavior available for comparison until replacement decisions
  and feature verification are complete. Provider implementations explicitly marked for
  removal may remain only in Git history and migration fixtures.

#### Legacy Inventory

The migration plan must account for these current groups without assuming they survive:

- Snitch notifications and member or message auditing.
- Server tools, role operations, permission toggles, voice tools, and thread bumping.
- Anti-raid, suspicious words, regex rules, impersonator alerts, and scammer alerts.
- Scheduled posts, RSS, role messages, auto replies, copiers, proxies, and broadcasts.
- Legacy market data and Twitter/X configuration, web applications, and webhook mapping.

For each group, record its event sources, permissions, configuration, side effects,
external dependencies, and acceptance tests before implementation.

## Testing and Verification

### Test Strategy

- Unit-test domain decisions with Discord objects represented by small fixtures or
  adapters.
- Integration-test module registration, configuration failure, permissions, scheduling,
  and graceful shutdown.
- Use contract tests around external provider adapters; do not make ordinary tests depend
  on live Discord or third-party APIs.
- Include tests for retries, duplicate events, partial caches, rate limits, and denied
  permissions where relevant.
- Verify the Docker image starts with the documented minimum configuration and stops
  cleanly.
- Never exercise real moderation actions against a production guild during automated
  verification.

### Required Verification

Run the root and affected workspace checks, build the production bot, and verify the
container starts and stops with the documented minimum configuration.
