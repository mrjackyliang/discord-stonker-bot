Protect the bot's settings and history by backing up the database with `pg_dump` and keeping a separate copy of the <Terminology title="The key that locks your secrets; back it up with the database" to="/docs/reference/terminology#appliance-and-services">installation key</Terminology>.

## The Data Volume

The container keeps everything in one <Terminology title="The Docker volume where all your data lives" to="/docs/reference/terminology#appliance-and-services">data volume</Terminology> at `/data`. With `docker run`, it is the host folder you pass with `-v`, such as `/volume1/docker/discord-stonker-bot`. Compose mounts a volume named `stonker-data`, and `docker volume ls` lists it as `discord-stonker-bot_stonker-data`.

| Path                          | What it holds                                                                                                                                                                                                                                      |
|-------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `/data/postgres`              | The PostgreSQL database, with every setting, account, token, <Terminology title="A public page that hands out short-lived Discord invites" to="/docs/reference/terminology#invite-page-and-webhooks">invite page</Terminology> image, job, and log |
| `/data/keys/installation.key` | The <Terminology title="The key that locks your secrets; back it up with the database" to="/docs/reference/terminology#appliance-and-services">installation key</Terminology> that encrypts stored secrets                                         |

`docker compose down` keeps the volume, and only `docker compose down --volumes` deletes it.

## The Installation Key

The <Terminology title="One container that holds the bot, panel, worker, and database" to="/docs/reference/terminology#appliance-and-services">appliance</Terminology> creates the <Terminology title="The key that locks your secrets; back it up with the database" to="/docs/reference/terminology#appliance-and-services">installation key</Terminology> on its first start, with permissions that only the services' user can read. It encrypts the <Terminology title="The bot's password for Discord, from the Developer Portal" to="/docs/reference/terminology#discord-basics">Bot Token</Terminology>, every feature secret, every <Terminology title="A phone app that makes six-digit sign-in codes" to="/docs/reference/terminology#sign-in-security">authenticator app</Terminology> secret, and the <Terminology title="Destination setting that's saved but never shown again" to="/docs/reference/terminology#notifications">secret fields</Terminology> of every [notification](/docs/control-panel/notifications/) <Terminology title="One place alerts go, such as a chat, topic, or inbox" to="/docs/reference/terminology#notifications">destination</Terminology>.

Accounts, passwords, <Terminology title="Sign in with Face ID, Touch ID, or a security key" to="/docs/reference/terminology#sign-in-security">passkeys</Terminology>, sessions, and <Terminology title="A key that lets your scripts call the panel's API as you" to="/docs/reference/terminology#accounts-and-access">access tokens</Terminology> don't use the key, because the panel stores hashes or public keys for them. A `pg_dump` backup doesn't include the key.

### Keys From Version 4.0

Version 4.0 kept the key at `/data/secrets/credential.key`. On the first start of a newer version, the <Terminology title="One container that holds the bot, panel, worker, and database" to="/docs/reference/terminology#appliance-and-services">appliance</Terminology> moves that file to `/data/keys/installation.key`, keeps its contents and permissions, and removes the `/data/secrets` folder once it's empty. Every saved secret keeps working, and the container log shows one `Moved the installation key` line.

If both files exist, the start uses `/data/keys/installation.key`, leaves `/data/secrets/credential.key` alone, and logs a warning. Remove the old file once you're sure you don't need it.

### If the Key File Is Missing

When the key file is gone but the database holds secrets the old key encrypted, the next start makes a new key and removes those secrets. Everything else stays, including feature settings, accounts, passwords, <Terminology title="Sign in with Face ID, Touch ID, or a security key" to="/docs/reference/terminology#sign-in-security">passkeys</Terminology>, sessions, <Terminology title="A key that lets your scripts call the panel's API as you" to="/docs/reference/terminology#accounts-and-access">access tokens</Terminology>, and logs.

- **<Terminology title="The bot's password for Discord, from the Developer Portal" to="/docs/reference/terminology#discord-basics">Bot Token</Terminology>** — The bot can't sign in until you enter the token again on the **Connection** page.
- **Feature secrets** — Webhook URLs, API keys, and signing secrets are removed, but each feature keeps its other settings, so only the secret fields need filling again.
- **<Terminology title="A phone app that makes six-digit sign-in codes" to="/docs/reference/terminology#sign-in-security">Authenticator apps</Terminology>** — Each one is turned off, the same as **Turn off**, along with its <Terminology title="A one-time backup code for when your authenticator is gone" to="/docs/reference/terminology#sign-in-security">recovery codes</Terminology>, so nobody is locked out. Its user signs in with a password or a <Terminology title="Sign in with Face ID, Touch ID, or a security key" to="/docs/reference/terminology#sign-in-security">passkey</Terminology>, then sets the app up again on **Sign-in and security**.
- **Notification <Terminology title="One place alerts go, such as a chat, topic, or inbox" to="/docs/reference/terminology#notifications">destinations</Terminology>** — Each one keeps its name, service, <Terminology title="Something the bot can alert you about" to="/docs/reference/terminology#notifications">events</Terminology>, and plain fields, but loses its <Terminology title="Destination setting that's saved but never shown again" to="/docs/reference/terminology#notifications">secret fields</Terminology>, so it gets no alerts until you enter them again on **Notifications**.

The <Terminology title="One container that holds the bot, panel, worker, and database" to="/docs/reference/terminology#appliance-and-services">appliance</Terminology> writes one `credential_key_replaced` warning to the container log that names each removed secret. The line never appears on the **Logs** page.

```bash
docker logs discord-stonker-bot | grep credential_key_replaced
docker compose logs app | grep credential_key_replaced
```

```json title="The installation key line"
{"component":"migration","context":{"message":"No installation key was found at /data/keys/installation.key, so Stonker Bot for Discord made a new one. These saved secrets were locked with the old key and were removed: the Bot Token, the <Feature> secrets for <Server>, the authenticator app for <username>, the <Name> notification. Enter them again in the control panel."},"event":"credential_key_replaced","level":"warn","timestamp":"2026-10-25T12:30:00.000Z"}
```

Notification <Terminology title="One place alerts go, such as a chat, topic, or inbox" to="/docs/reference/terminology#notifications">destinations</Terminology> that kept working, because they have no <Terminology title="Destination setting that's saved but never shown again" to="/docs/reference/terminology#notifications">secret fields</Terminology>, also get a **Saved secrets were removed** alert with the same list, as described in [Notifications](/docs/control-panel/notifications/#after-a-lost-installation-key).

When nothing depended on the old key, such as on a fresh install, there's no warning and no notice.

### The Saved Secrets Notice

After a new key replaces a lost one, the control panel shows **Saved secrets were removed** at the top of every page, with the date the new key was made and a link for each removed secret.

- **<Terminology title="The bot's password for Discord, from the Developer Portal" to="/docs/reference/terminology#discord-basics">Bot Token</Terminology>** — **Enter the Bot Token** opens the **Connection** page.
- **Feature secrets** — One link per feature and server, in the form `Enter the <Feature> secrets for <Server>`, opens that feature in that server.
- **<Terminology title="A phone app that makes six-digit sign-in codes" to="/docs/reference/terminology#sign-in-security">Authenticator app</Terminology>** — **Set up the authenticator app** opens **Sign-in and security**.
- **Notification <Terminology title="One place alerts go, such as a chat, topic, or inbox" to="/docs/reference/terminology#notifications">destinations</Terminology>** — One link per <Terminology title="One place alerts go, such as a chat, topic, or inbox" to="/docs/reference/terminology#notifications">destination</Terminology>, in the form `Set up the <Name> notification again`, opens **Notifications**.

- **Entering a secret again** — Saving the <Terminology title="The bot's password for Discord, from the Developer Portal" to="/docs/reference/terminology#discord-basics">Bot Token</Terminology> or the feature, turning the <Terminology title="A phone app that makes six-digit sign-in codes" to="/docs/reference/terminology#sign-in-security">authenticator app</Terminology> back on, or saving the notification <Terminology title="One place alerts go, such as a chat, topic, or inbox" to="/docs/reference/terminology#notifications">destination</Terminology> with every removed secret takes its link off the notice. ### If the Key File Belongs to Another Database

A key file that doesn't match the database, such as one from another install, stops startup instead. The <Terminology title="One container that holds the bot, panel, worker, and database" to="/docs/reference/terminology#appliance-and-services">appliance</Terminology> logs `migration_failed` with this error, and the bot, the control panel, and the <Terminology title="Background service that runs schedules and deliveries" to="/docs/reference/terminology#appliance-and-services">worker</Terminology> don't start:

```text
The installation key at /data/keys/installation.key doesn't belong to this database. Put back the key file this database was created with, or delete /data/keys/installation.key and restart to make a new key, then enter the saved secrets again.
```

Every start stops the same way until you put back the key file this database was created with. Deleting the key file instead makes a new one on the next start, as described in [If the Key File Is Missing](/docs/operations/storage-and-backups/#if-the-key-file-is-missing).

## Back Up the Database

Run `pg_dump` inside the container and write a custom-format dump to the Docker host. It connects over PostgreSQL's Unix socket, so it needs no password.

```bash title="docker run"
sudo docker exec --user 9999:9999 discord-stonker-bot sh -c \
  'pg_dump --host=/run/postgresql --username="${POSTGRES_USER:-stonker}" --dbname="${POSTGRES_DB:-stonker}" --format=custom' \
  > stonker.dump
```

```bash title="Docker Compose"
docker compose exec --no-TTY --user "${PUID:-1000}:${PGID:-1000}" app sh -c \
  'pg_dump --host=/run/postgresql --username="${POSTGRES_USER:-stonker}" --dbname="${POSTGRES_DB:-stonker}" --format=custom' \
  > stonker.dump
```

With `docker run`, use your own `PUID` and `PGID` in place of `9999:9999`.

It is recommended to store the dump away from the Docker host, keep a copy of the <Terminology title="The key that locks your secrets; back it up with the database" to="/docs/reference/terminology#appliance-and-services">installation key</Terminology> with the same care as a password, and test a restore before you rely on it.

## Restore From a Backup

A restore needs the database dump and the <Terminology title="The key that locks your secrets; back it up with the database" to="/docs/reference/terminology#appliance-and-services">installation key</Terminology> from the same <Terminology title="One container that holds the bot, panel, worker, and database" to="/docs/reference/terminology#appliance-and-services">appliance</Terminology>.

A new container makes its own key on its first start, while a dump restored into it brings back the old database's key check. The next start then stops with the error in [If the Key File Belongs to Another Database](/docs/operations/storage-and-backups/#if-the-key-file-belongs-to-another-database).

- **With the old key** — Copy the old install's `installation.key` (`credential.key` from a version 4.0 install), or the copy you kept with the backup, over `/data/keys/installation.key`, then restart the container. The restored <Terminology title="The bot's password for Discord, from the Developer Portal" to="/docs/reference/terminology#discord-basics">Bot Token</Terminology>, feature secrets, and <Terminology title="A phone app that makes six-digit sign-in codes" to="/docs/reference/terminology#sign-in-security">authenticator apps</Terminology> keep working.
- **Without the old key** — Delete `/data/keys/installation.key` and restart. The start makes a new key and removes the restored secrets, and the notice lists them to enter again, as described in [If the Key File Is Missing](/docs/operations/storage-and-backups/#if-the-key-file-is-missing).

## Network Storage

PostgreSQL expects the behavior of a local filesystem. It is recommended to keep the <Terminology title="The Docker volume where all your data lives" to="/docs/reference/terminology#appliance-and-services">data volume</Terminology> on local disk and copy `pg_dump` backups to a NAS or other remote storage, instead of placing the live database on NFS or SMB.

## Growth Over Time

The <Terminology title="One container that holds the bot, panel, worker, and database" to="/docs/reference/terminology#appliance-and-services">appliance</Terminology> never deletes old log entries or finished jobs, so the database grows as the bot runs. <Terminology title="A public page that hands out short-lived Discord invites" to="/docs/reference/terminology#invite-page-and-webhooks">Invite page</Terminology> images are the exception: saving the <Terminology title="A public page that hands out short-lived Discord invites" to="/docs/reference/terminology#invite-page-and-webhooks">invite page</Terminology> deletes the uploads it no longer uses.

## Delete Everything

:::danger
`docker compose down --volumes` permanently deletes the database and the <Terminology title="The key that locks your secrets; back it up with the database" to="/docs/reference/terminology#appliance-and-services">installation key</Terminology>.
:::
